# Simplifying Immutability with Java Records
#tag EN/Java

## What are Java Records?

**Records** are a special type of **class** introduced in Java to help **decrease boilerplate code**. They serve as "**data carriers**" for **immutable objects.** A Record automatically generates a class with its **canonical constructor**, **accessor methods** (called getters), `hashCode()`, `equals()`, and `toString()` implementations. The true essence of a Record is to **encapsulate a fixed conjunction of attributes** that represent the **state of an object** in a **concise and transparent** way.

---

## Advantages of Using Records in Java

- **Decreases boilerplate code** in **Plain Old Java Objects (POJOs)** and **Data Transfer Objects (DTOs)**.
- **Increases maintainability** due to less code and clearer intent.
- **Promotes immutability by default**, leading to safer and more predictable code.

---
## Declaring a Record Class 

```java
access_modifier record ClassName(list of components) {}

// A simple record to represent a person
public record Person(String firstName, String lastName) {}

// A record class to represent 2D dimensions and coordinates
record Point(double x, double y) {} [5, 8]

// A record for the dimensions of a rectangle
record Rectangle(double length, double width) {} [4]
```

Records can also implement **generics** to create data structures, for example:
```java
record Triangle<C extends Coordinate> (C top, C left, C right) {}
```

---
## Field private and Accessor methods (Getters)
The main pillar of records is their immutability, which is generated automatically for JVM. For each attribute declared, it generates a **private final field** with the same name as the field. This field is called the "component field". To use these attributes, records generate accessor methods with the same name. For example, for `record Point(double x, double y) {}`, the getters are `p.x()` and `p.y()`, different from the traditional convention of using `getX()` and `getY()` with POJOs.

---
## The Canonical Constructor

All records have a canonical constructor, which is a public constructor automatically generated by the JVM. This constructor accepts parameters with the same names and types as each component declared in the record. The term "canonical" means it's the standard, complete constructor that initializes all fields of the record.

Example: 
```java
public record ProductRequest(String name, BigDecimal price) {} [1]  
  
//Using the canonical constructor
ProductRequest product = new ProductRequest("Laptop", new BigDecimal("1200.00"));
```
The canonical constructor ensures that all component fields are properly initialized when a record instance is created, maintaining the immutability guarantee of records.

## Default Implementations of equals(), hashCode(), and toString()

In addition to fields and the canonical constructor, the Java compiler automatically generates default implementations for the `toString()`, `equals()`, and `hashCode()` methods. These implementations are based on the values of all record components, ensuring that the behavior of these methods is consistent with the "data carrier" nature of records.

**Method Implementations:**

- The `equals()` implementation determines that two record objects are considered equal if they are of the same record type and all their components contain equal values. For reference type components, the comparison is made using `Objects.equals()`; for primitive types, the `compare()` method of the corresponding wrapper class is used (for example, `Integer.compare()` for int).
- The `toString()` implementation produces a string representation that includes the names and values of all record components. For example, for a `Point(1.0, 0.0)`, the `toString()` might return `"Point[x=1.0, y=0.0]"`.
- The `hashCode()` implementation is consistent with `equals()`, ensuring that objects considered equal by `equals()` have the same hash value.

**Non-Normative Nature:**

It is crucial to understand that the default implementations of `hashCode()`, `equals()`, and `toString()` provided by the JDK are _not normative_. This means that the exact details of their behavior, such as the specific formula for combining hash codes, the order of comparisons in `equals()`, or the precise format of the `toString()` output, may be changed in future versions of Java.

This design choice provides flexibility to JVM and compiler implementers to optimize these methods without compromising compatibility. For example, the `toString()` implementation may be optimized for performance, or `hashCode()` may employ different algorithms in the future. The use of `invokedynamic` for these methods, as observed in the bytecode structure, supports this dynamic optimization.

**Implications for Developers:**

For developers, this means that while the _contract_ (e.g., symmetry of `equals`, consistency of `hashCode` with `equals`) is guaranteed, the _exact representation or calculation_ is not. This reinforces the fundamental principle of robust software engineering: programming to interfaces and contracts rather than relying on concrete implementations.

Consequently, tests should focus on validating the contract (e.g., `p.equals(copy)` should be true) rather than specific string formats or hash values. This approach ensures code remains robust across different Java versions and implementations.

**Members Automatically Generated by a Record**

The following table illustrates the members that the Java compiler automatically generates from a concise record declaration, using `record Person(String firstName, String lastName)` as an example. This demonstrates the significant reduction in boilerplate that records offer.

| Record Component<br/>(Ex: record Person(String firstName, String lastName)) | Automatically Generated Member                           | Description                                                                    |
| --------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------ |
| firstName (String)                                                          | `private final String firstName;`                        | Private and final instance field to store the component value.                 |
| lastName (String)                                                           | `private final String lastName;`                         | Private and final instance field to store the component value.                 |
| (Implicit)                                                                  | `public Person(String firstName, String lastName) {...}` | The canonical constructor that initializes all components.                     |
| firstName                                                                   | `public String firstName() {...}`                        | Public accessor method for the firstName component.                            |
| lastName                                                                    | `public String lastName() {...}`                         | Public accessor method for the lastName component.                             |
| (Implicit)                                                                  | `public boolean equals(Object o) {...}`                  | Default implementation that compares all components for equality.              |
| (Implicit)                                                                  | `public int hashCode() {...}`                            | Default implementation that generates a hash code based on all components.     |
| (Implicit)                                                                  | `public String toString() {...}`                         | Default implementation that returns a string representation of the components. |

This table clearly shows how a simple record declaration automatically provides all the essential functionality typically required for data carrier classes, eliminating the need for manual implementation of these common methods.
