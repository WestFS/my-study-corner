# 1. Simplifying Immutability with Java Records
#tag EN/Java
## 1.1. What are Java Records?

**Records** are a special type of **class** introduced in Java to help **decrease boilerplate code**. They serve as "**data carriers**" for **immutable objects.** A Record automatically generates a class with its **canonical constructor**, **accessor methods** (called getters), `hashCode()`, `equals()`, and `toString()` implementations. The true essence of a Record is to **encapsulate a fixed conjunction of attributes** that represent the **state of an object** in a **concise and transparent** way.

## 1.2. The Problem Records Solve

Before Records, creating a simple data class in Java required extensive boilerplate code:

```java
// Traditional approach - lots of boilerplate
public class Person {
    private final String firstName;
    private final String lastName;
    
    public Person(String firstName, String lastName) {
        this.firstName = firstName;
        this.lastName = lastName;
    }
    
    public String getFirstName() { return firstName; }
    public String getLastName() { return lastName; }
    
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Person person = (Person) o;
        return Objects.equals(firstName, person.firstName) &&
               Objects.equals(lastName, person.lastName);
    }
    
    @Override
    public int hashCode() {
        return Objects.hash(firstName, lastName);
    }
    
    @Override
    public String toString() {
        return "Person{firstName='" + firstName + "', lastName='" + lastName + "'}";
    }
}
```

With Records, this becomes:

```java
// Records approach - concise and clear
public record Person(String firstName, String lastName) {}
```

## 1.3. Core Advantages of Records

- **Dramatic Reduction in Boilerplate Code**: Records eliminate the need to manually write constructors, accessors, and standard methods, reducing code by up to 80-90% in data classes.
- **Enhanced Maintainability**: With less code to maintain, there are fewer opportunities for bugs. Changes to the data structure require only updating the record declaration.
- **Immutability by Default**: Records promote immutable design patterns, leading to safer, more predictable code that's easier to reason about and debug.
- **Automatic Consistency**: The compiler ensures that `equals()`, `hashCode()`, and `toString()` implementations are always consistent with each other and with the record's components.

# 2. Record Declaration and Syntax

## 2.1. Basic Declaration Structure

```java
[access_modifier] record RecordName(ComponentType1 component1, ComponentType2 component2, ...) {
    // Optional: additional constructors, methods, static members
}
```

## 2.2. Practical Examples

```java
// Simple geometric point
public record Point(double x, double y) {}

// Customer information for business applications
public record Customer(String id, String name, String email, LocalDate registrationDate) {}

// Product with price information
public record Product(String name, String category, BigDecimal price, boolean inStock) {}

// Generic record for key-value pairs
public record Pair<K, V>(K key, V value) {}

// Complex nested record
public record Address(String street, String city, String zipCode) {}
public record Employee(String name, Address address, Department department) {}

```

## 2.3. Records with Generics

Records support full generic functionality, making them highly reusable:

```java
// Generic container
public record Box<T>(T content) {
    public boolean isEmpty() {
        return content == null;
    }
}

// Multiple type parameters
public record Triple<A, B, C>(A first, B second, C third) {}

// Bounded type parameters
public record Coordinate<T extends Number>(T x, T y) {
    public double distance() {
        return Math.sqrt(x.doubleValue() * x.doubleValue() + 
                        y.doubleValue() * y.doubleValue());
    }
}

record Triangle<C extends Coordinate> (C top, C left, C right) {}

```

# 3. Field Private and Accessor Methods (Getters)

The main pillar of records is their immutability, which is generated automatically for JVM. For each attribute declared, it generates a **private final field** with the same name as the field. This field is called the "component field". To use these attributes, records generate accessor methods with the same name. For example, for `record Point(double x, double y) {}`, the getters are `p.x()` and `p.y()`, different from the traditional convention of using `getX()` and `getY()` with POJOs.

## 3.1. The Canonical Constructor

All records have a canonical constructor, which is a public constructor automatically generated by the JVM. This constructor accepts parameters with the same names and types as each component declared in the record. The term "canonical" means it's the standard, complete constructor that initializes all fields of the record.

Example:

```java
public record ProductRequest(String name, BigDecimal price) {}
  
//Using the canonical constructor
ProductRequest product = new ProductRequest("Laptop", new BigDecimal("1200.00"));
```

The canonical constructor ensures that all component fields are properly initialized when a record instance is created, maintaining the immutability guarantee of records.

## 3.2. Default Implementations of equals(), hashCode(), and toString()

In addition to fields and the canonical constructor, the Java compiler automatically generates default implementations for the `toString()`, `equals()`, and `hashCode()` methods. These implementations are based on the values of all record components, ensuring that the behavior of these methods is consistent with the "data carrier" nature of records.

**Method Implementations:**

- The `equals()` implementation determines that two record objects are considered equal if they are of the same record type and all their components contain equal values. For reference type components, the comparison is made using `Objects.equals()`; for primitive types, the `compare()` method of the corresponding wrapper class is used (for example, `Integer.compare()` for int).
- The `toString()` implementation produces a string representation that includes the names and values of all record components. For example, for a `Point(1.0, 0.0)`, the `toString()` might return `"Point[x=1.0, y=0.0]"`.
- The `hashCode()` implementation is consistent with `equals()`, ensuring that objects considered equal by `equals()` have the same hash value.

**Non-Normative Nature:**

It is crucial to understand that the default implementations of `hashCode()`, `equals()`, and `toString()` provided by the JDK are _not normative_. This means that the exact details of their behavior, such as the specific formula for combining hash codes, the order of comparisons in `equals()`, or the precise format of the `toString()` output, may be changed in future versions of Java.

This design choice provides flexibility to JVM and compiler implementers to optimize these methods without compromising compatibility. For example, the `toString()` implementation may be optimized for performance, or `hashCode()` may employ different algorithms in the future. The use of `invokedynamic` for these methods, as observed in the bytecode structure, supports this dynamic optimization.

**Implications for Developers:**

For developers, this means that while the _contract_ (e.g., symmetry of `equals`, consistency of `hashCode` with `equals`) is guaranteed, the _exact representation or calculation_ is not. This reinforces the fundamental principle of robust software engineering: programming to interfaces and contracts rather than relying on concrete implementations.

Consequently, tests should focus on validating the contract (e.g., `p.equals(copy)` should be true) rather than specific string formats or hash values. This approach ensures code remains robust across different Java versions and implementations.

## 3.3. Members Automatically Generated by a Record

The following table illustrates the members that the Java compiler automatically generates from a concise record declaration, using `record Person(String firstName, String lastName)` as an example. This demonstrates the significant reduction in boilerplate that records offer.

|Record Component<br/>(Ex: record Person(String firstName, String lastName))|Automatically Generated Member|Description|
|---|---|---|
|firstName (String)|`private final String firstName;`|Private and final instance field to store the component value.|
|lastName (String)|`private final String lastName;`|Private and final instance field to store the component value.|
|(Implicit)|`public Person(String firstName, String lastName) {...}`|The canonical constructor that initializes all components.|
|firstName|`public String firstName() {...}`|Public accessor method for the firstName component.|
|lastName|`public String lastName() {...}`|Public accessor method for the lastName component.|
|(Implicit)|`public boolean equals(Object o) {...}`|Default implementation that compares all components for equality.|
|(Implicit)|`public int hashCode() {...}`|Default implementation that generates a hash code based on all components.|
|(Implicit)|`public String toString() {...}`|Default implementation that returns a string representation of the components.|

This table clearly shows how a simple record declaration automatically provides all the essential functionality typically required for data carrier classes, eliminating the need for manual implementation of these common methods.

# 4. Java Records: Advanced Features and Customizations

## 4.1. Overview

Java records are designed for simplicity and immutability, but the language provides mechanisms to customize their behavior and extend their capabilities while maintaining conciseness.

## 4.2. Constructor Types in Records

### 4.2.1. Custom Constructors

Records can have additional constructors beyond the automatically generated canonical constructor. However, there's a fundamental rule:

**Key Rule**: The first statement of any custom constructor must invoke another constructor of the record using `this(...)`, ensuring that ultimately the canonical constructor is called to initialize all components.

**Example:**

```java
record Point(double x, double y) {
    public Point() { // Custom constructor for origin point
        this(0, 0); // Calls the canonical constructor
    }
}
```

### 4.2.2. Compact Canonical Constructor

This is a more concise way to provide a custom implementation of the canonical constructor.

**Key Features:**

- Constructor parameters and instance field initialization are omitted explicitly
- The compact constructor body executes **before** parameters are assigned to corresponding instance fields
- Particularly useful for validation or normalization of components before they are finalized

**Example:**

```java
record Point(double x, double y) {
    public Point { // Compact canonical constructor
        // Validation or transformation logic before final field assignment
        if (x == y || x == -y) {
            onDiagonal++; // Example logic
        }
    }
    
    public static int onDiagonal = 0; // Static fields are allowed
}
```

### 4.2.3. Critical Design Detail

The fact that parameter assignment to instance fields occurs at the end of the compact canonical constructor is a crucial design feature. This means:

- **Inside the compact constructor body**: Instance fields are not yet initialized
- **Parameters are accessible**: Constructor parameters (with the same names as fields) can be read and even modified
- **Validation opportunity**: This functionality is essential for implementing validation and data transformation logic before the record object becomes completely formed and immutable

### 4.2.4. Benefits

This design allows developers to:

- Validate input data before object creation
- Transform or normalize data during construction
- Maintain the immutability guarantee while providing flexibility
- Keep the code concise and readable

## 4.3. Adding Instance and Static Methods

Records are not just passive data containers; they can contain business logic relevant to their components. It's possible to add any number of instance methods and static methods to a record, just as in a regular Java class.

**Instance Methods:** Allow adding behavior that operates on the record's data.

```java
record Point(double x, double y) {
    public double distance(Point q) { // Instance method
        return Math.sqrt(Math.pow(x - q.x, 2) + Math.pow(y - q.y, 2));
    }
}
```

Additionally, it's possible to provide custom implementations for automatically generated methods (toString, equals, hashCode) if the default behavior is not suitable for a specific use case.

```java
record Point(double x, double y) {
    @Override
    public String toString() {
        return "(" + x + ", " + y + ")"; // Custom toString implementation
    }
}
```

**Static Methods and Static Fields:** Records can declare static fields and methods, which belong to the record class itself, not to a specific instance.

```java
record Point(double x, double y) {
    public static final Point ORIGIN = new Point(0, 0); // Static field
    
    public static double calculateDistance(Point p1, Point p2) { // Static method
        return p1.distance(p2);
    }
}
```

## 4.4. Interface Implementation and Generic Records

Despite their inheritance restrictions (discussed in the Limitations section), records are flexible enough to implement interfaces and be generic, allowing them to participate in type hierarchies and polymorphic designs.

**Interface Implementation:** A record can implement one or more interfaces, just like a regular class. This is useful for defining behavioral contracts that records must follow.

```java
record Customer(String id, String name) implements Billable {}

record Point(double x, double y) implements Comparable<Point> {
    @Override
    public int compareTo(Point other) {
        int dx = Double.compare(x, other.x);
        return dx != 0 ? dx : Double.compare(y, other.y);
    }
}
```

The ability to implement interfaces allows records to integrate seamlessly into frameworks and APIs that depend on polymorphism, without sacrificing the conciseness and immutability they offer. This means that records are not merely "data bags," but can act as complete data types that participate in behaviors defined by contracts.

**Generic Records:** Records can be parameterized by types, making them "generic records." This allows them to work with different data types safely and reusably.

```java
record Box<T>(T content) {}
record Pair<K, V>(K key, V value) {}
```

Additionally, annotations on record components can be propagated to the generated fields and constructors, depending on the @Target of the annotation. This enables the use of validation annotations or persistence framework annotations directly in the concise record declaration.

## 4.5. Data Validation in Records

Data validation is a critical aspect in building robust systems. In records, input data validation is ideally performed within the compact canonical constructor. Since the compact constructor body executes before parameter values are assigned to the record's final fields, it offers a perfect control point to ensure data integrity at the moment of object creation. If validation fails, the constructor can throw an exception, preventing the creation of an invalid record instance.

**Example of Validation and Normalization:**

```java
record PositiveNumber(int value) {
    public PositiveNumber { // Compact canonical constructor
        if (value <= 0) {
            throw new IllegalArgumentException("Value must be positive");
        }
    }
}

record PolarPoint(double r, double theta) {
    public PolarPoint { // Angle normalization
        theta = Math.IEEEremainder(theta, 2 * Math.PI);
        if (theta < 0) theta += 2 * Math.PI;
    }
}
```

This validation capability in the constructor ensures that any created record instance is valid from the start, reinforcing immutability and data reliability. It's a direct benefit of the compact constructor design, which allows data transformation and verification before final assignment.

## 4.6. Limitations and Restrictions of Records

Despite their advantages, records have certain limitations and design restrictions that are intrinsic to their nature and purpose. Understanding these restrictions is crucial for deciding when to use records and when to opt for traditional classes.

### 4.6.1. Immutability and the final Nature of Fields

Immutability is a fundamental characteristic of records. All fields of a record are implicitly declared as `private final`. This means that once a record object is created and its components are initialized through the canonical constructor, their values cannot be changed. The `final` nature of fields is a guarantee that the record's state remains constant throughout its lifetime. This restriction is one of the main reasons for the conciseness and thread safety that records offer, as it eliminates the need for concerns about unexpected state modifications.

### 4.6.2. Absence of Explicit Inheritance (Implicitly final)

Records are implicitly `final` and therefore cannot be extended by other classes or records. Similarly, a record cannot extend any other class, not even another record. This restriction stems from the fact that all records implicitly extend the abstract class `java.lang.Record`. Since Java doesn't support multiple inheritance, a record cannot inherit from another class.

Although records don't support the traditional inheritance model, they can participate in type hierarchies in a controlled manner through the use of the `sealed` keyword. This allows a record to declare a limited set of permitted subtypes, offering a form of restricted polymorphism without the complexity of traditional inheritance. This approach is an alternative to the inheritance model, providing a mechanism to control extensibility in a more explicit and safe way.

### 4.6.3. Restrictions on Declaring Additional Instance Fields

The "data carrier" nature of records implies that their state is completely determined by the components declared in the header. Consequently, records cannot have any other instance variables besides the "record components". This means it's not possible to add instance fields that are not part of the canonical constructor's component list. This restriction ensures that the record's structure is transparent and that its state is always obvious from its declaration.

# 5. Records vs. Traditional POJOs: A Comparative Analysis

The introduction of records offers a powerful alternative to traditional POJOs (Plain Old Java Objects) for data modeling. Understanding the differences and ideal use cases for each is fundamental for effective software design.

## 5.1. Advantages and Disadvantages of Each Approach

The choice between records and POJOs depends on a project's specific needs, especially regarding mutability, behavioral complexity, and compatibility.

Records are a native feature of the Java language, which gives them inherent advantages over third-party libraries like Lombok. Being part of the JDK, records are inherently supported by all Java tools and IDEs, without requiring additional plugins or configurations. This simplifies project setup and reduces dependency on external tools. The comparison with Lombok is crucial, as both aim to reduce boilerplate, but records do so at the language level, which has implications for build configuration, team familiarity, and code longevity.

### 5.1.1. Table 1: Comparison: Java Records vs. Traditional POJOs

|Feature|Java Records|Traditional POJOs|
|---|---|---|
|**Syntax**|Extremely concise, one-line declaration|Verbose, requires explicit field declarations, constructors, methods|
|**Boilerplate**|Minimal; automatically generated by compiler|High; requires manual writing or use of libraries (e.g., Lombok)|
|**Mutability**|Immutable by default; all fields are final|Mutable by default; requires additional effort to be immutable|
|**Inheritance**|Does not support explicit inheritance (implicitly final, extends java.lang.Record). Can use sealed for type hierarchies|Supports traditional inheritance (class extension)|
|**Generated Methods**|Canonical constructor, accessors (.field()), equals(), hashCode(), toString() automatically generated|Methods (getters, setters, constructors, equals(), hashCode(), toString()) must be written manually or generated by IDE/Lombok|
|**Customization**|Limited to instance/static methods and compact/custom constructors|Highly flexible; allows any logic and structure|
|**Use Cases**|Ideal for DTOs, value objects, configurations, event payloads, immutable data structures|General use; mutable objects, complex business logic encapsulation, inheritance hierarchies|
|**Java Compatibility**|Available from Java 16 (preview in Java 14/15)|Compatible with all Java versions|
|**Tools/Dependencies**|Native language feature; inherent support by IDEs and Java tools|May require Lombok for boilerplate reduction, adding dependency and IDE configuration needs|

## 5.2. Recommended Use Cases for Records (DTOs, Value Objects, Configurations, Events)

Records shine in scenarios where immutability, simplicity, and clarity are priorities. They are ideal for representing data that should not change after creation and where the focus is on data structure, not complex behavior.

### 5.2.1. Data Transfer Objects (DTOs) and API Response Models

Records are perfect for DTOs in microservices architectures or for response models in RESTful APIs, where immutability ensures thread safety and data integrity during transfer.

```java
public record UserResponse(String name, int age, String email) {}
```

### Value Objects

For representing values like coordinates, key-value pairs, or currencies, where identity is based on the values of their components.

```java
public record CacheEntry(String key, Object value) {}
```

### Configuration Data

For storing static application configuration values that should not be changed after initialization.

```java
public record AppConfig(String appName, int maxUsers) {}
```

### Database Query Results (Projections)

When retrieving only a subset of fields from a database entity, records allow creating lightweight and immutable projections.

```java
public record ProductSummary(String name, double price) {}
```

### Message Payloads in Event-Driven Systems

In event-based architectures, events should be immutable and easily serializable, requirements that records naturally meet.

```java
public record OrderEvent(String orderId, String status, Instant timestamp) {}
```

### Pattern Matching

Records are particularly beneficial when combined with newer Java features like pattern matching, which allows concise deconstruction of record values.

Records align well with Domain-Driven Design (DDD) principles for creating more robust and maintainable code. The inherent immutability of records supports thread safety, which is increasingly important in concurrent and distributed systems. Their use promotes data consistency and simplifies debugging, as the state of a record object is always predictable.

## 5.3. When to Continue Using POJOs (Mutable Objects, Complex Business Logic, Inheritance)

Despite the advantages of records, there are scenarios where traditional POJOs are still the most appropriate choice.

### Mutable Objects

If an object needs to have its fields updated after creation, records are not suitable as they are immutable by design. POJOs, which are mutable by default, are more flexible in these cases.

```java
class UserProfile { // Example of mutable class
    private String name;
    private int age;
    public void setName(String name) { this.name = name; }
    public void setAge(int age) { this.age = age; }
}
```

Scenarios involving complex workflows with frequent object state updates after creation are better served by POJOs.

### Complex Business Logic Encapsulation

When a data object needs to encapsulate complex business logic, intricate validation rules, or computed fields that depend on mutable internal state, traditional classes offer greater flexibility.

```java
class CustomerDTO { // Example with business logic
    private String name;
    private double balance;
    public double calculateDiscount() {
        return balance > 1000 ? 10 : 5;
    }
}
```

### Inheritance and Hierarchical Structures

Since records do not support inheritance (they are implicitly final and extend java.lang.Record), if the application design depends on polymorphism, abstract classes, or functionality extension via inheritance, POJOs are necessary.

```java
abstract class PersonDTO { 
    protected String name; 
    public abstract void display(); 
}
class EmployeeDTO extends PersonDTO { /*... */ }
```

### Compatibility with Older Java Versions

For projects still using Java versions prior to JDK 16, records are not an option. In these cases, traditional POJOs or libraries like Lombok are the alternatives for reducing boilerplate. Compatibility with older Java versions is a practical constraint for many corporate projects, meaning record adoption depends on the project's JDK baseline.

# 6. Record Patterns in Java 21+

Record Patterns, introduced in Java 21 (JEP 440), represent a significant evolution in the language's pattern matching capabilities, enhancing how data in records can be processed and deconstructed.

## 6.1. Deconstruction of Record Instances

Record Patterns allow concise deconstruction of record instances, simplifying the extraction of their component values. Instead of explicitly calling a record's accessor methods, Record Patterns allow components to be extracted directly into pattern variables during `instanceof` checks or in switch expressions.

### 6.1.1. Example with instanceof:

```java
record Point(double x, double y) {}

static void printAngleFromXAxis(Object obj) {
    if (obj instanceof Point(double x, double y)) { // Record Pattern
        System.out.println(Math.toDegrees(Math.atan2(y, x)));
    }
}
```

In this example, if `obj` is an instance of `Point`, the variables `x` and `y` are automatically initialized with the values of the corresponding record components. This eliminates the need for explicit casting and separate calls to `p.x()` and `p.y()`, making the code cleaner and more readable. It's important to note that the value `null` does not match any Record Pattern.

## 6.2. Nested Patterns and Type Inference

One of the most powerful capabilities of Record Patterns is their ability to be nested, allowing matching and deconstruction of complex and hierarchical data structures in an expressive way. This is particularly useful for processing data that contains records within other records.

### 6.2.1. Example of Nested Patterns:

```java
enum Color { RED, GREEN, BLUE }
record ColoredPoint(Point p, Color c) {}
record ColoredRectangle(ColoredPoint upperLeft, ColoredPoint lowerRight) {}

static void printXCoordOfUpperLeftPointWithPatterns(ColoredRectangle r) {
    if (r instanceof ColoredRectangle(ColoredPoint(Point(var x, var y), var upperLeftColor), var lowerRight)) {
        System.out.println("Processing rectangle with upper-left X: " + x);
    }
}
```

In this example, the Record Pattern deconstructs `ColoredRectangle` into `ColoredPoint`, which in turn deconstructs `Point` and extracts `x` and `y` directly.

Additionally, type inference can be used with `var` in the component list of a Record Pattern. The compiler is able to infer the types of type arguments and pattern variables, making the code even more concise.

### 6.2.2. Example of Type Inference with var:

```java
record Box<T>(T t) {}

static void printBoxContentsAgain(Box<String> bo) {
    if (bo instanceof Box(var s)) { // Compiler infers Box<String>(String s)
        System.out.println("Box contains: " + s);
    }
}

static void nestedBox(Box<Box<String>> bo) {
    if (bo instanceof Box(Box(var s))) { // Compiler infers Box<Box<String>>(Box(String s))
        System.out.println("String " + s);
    }
}
```

Record Patterns significantly enhance pattern matching capabilities in Java, making code more declarative and readable for handling complex data structures. This is a major evolution in the language's expressiveness, allowing more idiomatic and efficient code for data processing.
