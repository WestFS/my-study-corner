

# **Compreendendo o Comportamento do hashCode() em Java Records: Cache, Otimizações e Implicações de Desempenho**

## **1\. Introdução aos Java Records: Um Portador de Dados Conciso**

Java Records, introduzidos como um recurso de pré-visualização no JDK 14 e padronizados no JDK 16 através da JEP 395, representam um tipo especializado de classe Java. O seu objetivo primordial é atuar como portadores de dados imutáveis, reduzindo significativamente o código repetitivo (boilerplate) tradicionalmente associado às Plain Old Java Objects (POJOs) que têm como função principal o armazenamento de dados.1 Esta funcionalidade permite que os desenvolvedores concentrem-se em aspetos mais críticos da lógica de aplicação.1  
A essência dos Records reside na sua capacidade de simplificar a declaração de classes que modelam dados. As suas características principais incluem a imutabilidade implícita, onde todos os componentes são campos private final, uma sintaxe de declaração concisa e a geração automática de métodos essenciais.8 Os Records são implicitamente  
final, o que significa que não podem ser estendidos por outras classes (eles estendem implicitamente java.lang.Record), mas podem implementar interfaces e ser genéricos.8  
A forma como os Records simplificam o desenvolvimento é evidente na geração automática dos métodos equals(), hashCode(), e toString(). Estas implementações são derivadas dos componentes do Record, garantindo igualdade e representação baseadas em valor.1 Por exemplo, para um Record  
Point com componentes x e y, a chamada p.toString() pode resultar na string "Point\[x=1.0, y=0.0\]".4 Esta automação reduz drasticamente as linhas de código em comparação com os POJOs tradicionais, tornando os Records ideais para Data Transfer Objects (DTOs), modelos de resposta de API e configurações de dados.1  
A introdução dos Records não é apenas uma melhoria sintática; representa uma mudança fundamental na modelagem de dados em Java. A ênfase na "redução de código repetitivo" e nos "portadores de dados imutáveis" 1 indica uma transição de um paradigma centrado em JavaBeans/POJOs mutáveis, onde o comportamento (getters/setters) era frequentemente central, para um paradigma mais funcional e centrado em dados, onde o estado é a preocupação principal e é inerentemente imutável. Esta abordagem alinha-se com as tendências de programação modernas que favorecem a imutabilidade para segurança de threads e previsibilidade. Tal mudança encoraja os desenvolvedores a projetar sistemas com um fluxo de dados mais claro e menos estado mutável, o que pode levar a bases de código mais robustas e fáceis de entender, especialmente em ambientes concorrentes. Promove implicitamente a semântica de "objetos de valor" em detrimento da semântica de "entidade" para dados simples.  
Além disso, a repetição da menção de métodos "gerados automaticamente" 8 significa que o compilador Java assume um papel mais ativo do que apenas traduzir o código-fonte. Ele sintetiza porções significativas da classe com base na declaração concisa do Record. Isto transfere a complexidade do código repetitivo escrito pelo desenvolvedor para as partes internas geridas pelo compilador. Esta delegação de responsabilidade reduz a carga cognitiva para os desenvolvedores e a área de superfície para bugs comuns, como implementações incorretas de  
equals/hashCode. Sugere também um futuro onde mais padrões comuns podem ser "incorporados" na linguagem através da síntese do compilador, em vez de depender apenas de bibliotecas externas (como Lombok) ou de codificação manual repetitiva.

## **2\. Compreendendo o Contrato do hashCode() em Java**

O método hashCode() em Java é um pilar fundamental para o desempenho de coleções baseadas em hash, como HashMap e HashSet. O seu contrato geral, conforme definido por java.lang.Object, impõe duas regras críticas. Primeiro, a **consistência**: sempre que invocado no mesmo objeto mais de uma vez durante a execução de uma aplicação Java, o método hashCode() deve retornar consistentemente o mesmo inteiro, desde que nenhuma informação utilizada nas comparações de equals no objeto seja modificada.14 Segundo, a  
**igualdade**: se dois objetos são considerados iguais de acordo com o seu método equals(), então a chamada do método hashCode() em cada um dos dois objetos deve produzir o mesmo resultado inteiro.14 Embora não seja estritamente exigido, é altamente desejável produzir códigos hash distintos para objetos desiguais, a fim de melhorar o desempenho das tabelas hash, minimizando colisões.14  
A implementação padrão de hashCode() herdada de java.lang.Object é frequentemente referida como o "código hash de identidade". Este código hash não se baseia no conteúdo do objeto, mas sim na sua identidade, que é tipicamente um valor relacionado com o seu endereço de memória, embora não seja diretamente o endereço no OpenJDK.15 No HotSpot JVM, o resultado da geração do código hash de identidade é calculado uma vez, na sua primeira solicitação, e depois é armazenado em cache no cabeçalho do objeto (especificamente, na  
*mark word*).15 Chamadas subsequentes a  
Object.hashCode() ou System.identityHashCode() para o mesmo objeto recuperam este valor em cache, tornando estas chamadas muito rápidas.17 É importante notar que a geração do código hash de identidade pode ser uma operação relativamente lenta na sua primeira chamada em comparação com as recuperações subsequentes em cache ou mesmo com os cálculos de código hash baseados em valor.17 Um efeito colateral significativo da chamada do método  
hashCode() padrão (ou System.identityHashCode()) num objeto no HotSpot é que ele torna o objeto inelegível para *biased locking*, o que pode ter impacto no desempenho da sincronização em cenários de baixa contenção.15  
A análise do comportamento do hashCode() revela uma dualidade fundamental. Existem duas abordagens distintas para o hashCode(): a baseada na identidade (herdada de Object, e otimizada com cache pela JVM) e a baseada em valor (calculada a partir dos componentes do objeto). A questão inicial do utilizador, ao perguntar sobre o cache do hashCode em Records, pode estar a confundir estas duas naturezas. A distinção entre o cache da JVM para o hashCode de *identidade* e a ausência de um cache explícito para o hashCode *baseado em valor* dos Records é crucial para uma compreensão precisa do desempenho e das decisões de design. Esta distinção sublinha que "cache" para hashCode é um conceito matizado em Java; enquanto a JVM otimiza o hashCode de identidade através de cache, isso não se estende automaticamente ao hashCode baseado em valor de classes personalizadas ou Records. Uma interpretação errada deste ponto pode levar a suposições incorretas sobre o desempenho ou a implementações falhas de equals/hashCode se se tentar implementar um cache manual para um hashCode baseado em valor sem as garantias de imutabilidade adequadas.  
Adicionalmente, a interação com as otimizações da JVM, como o *biased locking*, é um aspeto subtil mas importante. O facto de a chamada de Object.hashCode() desativar o *biased locking* 15 revela uma troca de desempenho. O  
*biased locking* é uma otimização da JVM para monitores sem contenção. Se um objeto é frequentemente usado para sincronização *e* o seu hashCode() é chamado, esta otimização é perdida. Para aplicações críticas em termos de desempenho, especialmente aquelas que dependem fortemente de blocos synchronized com baixa contenção, é necessário considerar cuidadosamente quando e se Object.hashCode() é chamado (ou se um hashCode() personalizado é fornecido). Isto demonstra as profundas interdependências entre funcionalidades aparentemente não relacionadas da JVM e chamadas de métodos da biblioteca padrão.

## **3\. Implementação do hashCode() em Java Records: Uma Análise Aprofundada**

Para os Java Records, o compilador gera automaticamente uma implementação de hashCode() que é *baseada em valor*. Isto significa que o código hash é derivado da combinação dos códigos hash de todos os componentes do Record.8 Esta abordagem garante que duas instâncias de Record são consideradas iguais (através de  
equals()) se forem do mesmo tipo e contiverem valores de componentes iguais, e, consequentemente, produzirão o mesmo hashCode(), aderindo ao contrato de Object.hashCode().8 É importante notar que o algoritmo preciso utilizado pelo JDK para combinar os códigos hash dos componentes (por exemplo,  
31 \* h1 \+ h2) *não é normativo* e está sujeito a alterações em futuras versões do Java. Os desenvolvedores não devem depender da fórmula exata ou da ordem das comparações de componentes.4

### **Os Java Records Cacheiam o seu Valor hashCode()?**

**Não, os Java Records não armazenam em cache *explicitamente* o seu hashCode *baseado em valor* num campo interno por padrão, ao contrário de java.lang.String**. O hashCode para um Record é *calculado* a partir dos seus componentes cada vez que hashCode() é chamado, a menos que a JVM aplique otimizações de tempo de execução específicas.4 O conceito de armazenar em cache o  
hashCode num campo é tipicamente uma otimização manual, como observado com String ou implementações personalizadas para EqualsVerifier 20, que envolve o armazenamento do código hash calculado num campo  
private final int durante a construção do objeto. Os Records não geram automaticamente tal campo para o seu código hash baseado em valor. A questão do utilizador pode decorrer de uma conceção errada comum de que todas as implementações de hashCode em classes imutáveis são explicitamente armazenadas em cache, de forma semelhante a String. É crucial distinguir entre o cache do hashCode de *identidade* pela JVM (para Object.hashCode()) e o hashCode *baseado em valor* para Records.

### **Otimizações da JVM para o hashCode() de Records (e.g., invokedynamic)**

Embora os Records não armazenem explicitamente em cache o seu código hash baseado em valor num campo, a Java Virtual Machine (JVM), particularmente o HotSpot, aplica otimizações significativas aos métodos gerados automaticamente, incluindo hashCode().10 Um mecanismo chave para esta otimização é a instrução  
invokedynamic, introduzida no Java 7 e amplamente utilizada por funcionalidades modernas da JVM, como Records e lambdas.11  
invokedynamic permite que a JVM adie a pesquisa e ligação exatas do método para o tempo de execução, possibilitando funcionalidades de linguagem dinâmicas e chamadas altamente otimizadas. Na primeira invocação, um "método bootstrap" é chamado para ligar o *call site* invokedynamic à implementação real do método. As chamadas subsequentes podem então ignorar este "caminho lento" e invocar diretamente o código otimizado.23 Esta otimização dinâmica significa que a JVM pode potencialmente gerar código de máquina altamente eficiente para métodos de Record, incluindo  
hashCode(), em tempo de execução. Isso pode levar a benefícios de desempenho, mesmo sem um cache explícito ao nível do campo, otimizando a própria *computação*.23 Os Records são "confiáveis" pela HotSpot VM de uma forma especial, contribuindo para a sua velocidade superior em alguns aspetos em comparação com as classes Java regulares.21  
A distinção entre cache implícita e explícita é fundamental aqui. A resposta central à questão do utilizador é "não, não há um cache explícito por padrão *dentro do Record*." No entanto, a nuance é que a própria JVM executa otimizações sofisticadas (como invokedynamic) que podem tornar o *cálculo* do código hash altamente eficiente.21 Esta é uma forma de otimização implícita em tempo de execução que alcança benefícios de desempenho sem exigir que o desenvolvedor gerencie um campo de cache. A distinção é crucial: o cache explícito é uma escolha de design para  
String, enquanto a otimização implícita é uma característica da JVM para Records. Isto realça os benefícios "ao nível da plataforma" dos Records. Ao serem uma construção de linguagem, os Records permitem que a JVM aplique otimizações profundas e não óbvias que não são facilmente alcançáveis com POJOs tradicionais ou mesmo Lombok, que depende do processamento de anotações e manipulação de bytecode em vez da "confiança" direta da JVM. Isto sugere que os Records não são apenas sobre sintaxe, mas também sobre permitir melhorias de desempenho mais profundas em tempo de execução.  
A implementação do hashCode para Records é explicitamente declarada como "não normativa" e "sujeita a alterações".4 Isto significa que a lógica interna exata (por exemplo, a fórmula  
31 \* h1 \+ h2) é um detalhe de implementação que pode evoluir. Esta é uma escolha de design deliberada da equipa do OpenJDK. Os desenvolvedores devem evitar depender de comportamentos internos específicos dos métodos de Record para além do seu contrato (por exemplo, o contrato de equals). Esta flexibilidade permite que a JVM introduza otimizações mais avançadas ou diferentes algoritmos de hash em futuras versões sem quebrar a compatibilidade, garantindo que os Records permaneçam performáticos e adaptáveis. Reforça a ideia de que os Records são uma "caixa preta" para o transporte de dados, onde o "como" é abstraído para o benefício da plataforma.

| Característica / Tipo | java.lang.Object (padrão) | java.lang.String | Java Records |
| :---- | :---- | :---- | :---- |
| **Tipo de Hash Code** | Baseado em identidade | Baseado em valor | Baseado em valor |

## **4\. Implicações e Comparações de Desempenho**

### **Desempenho do hashCode() de Records vs. POJOs Tradicionais e Lombok**

Benchmarks indicam que os Java Records podem oferecer um desempenho melhorado para hashCode() (e outros métodos gerados) em comparação com classes tradicionais ou mesmo equivalentes gerados por Lombok.10 Um benchmark específico demonstrou que os Records eram aproximadamente 10% mais rápidos do que as classes regulares num cenário específico.21 Esta vantagem de desempenho é atribuída à capacidade da JVM de aplicar otimizações especializadas aos Records, que são projetados como portadores de dados transparentes.10  
POJOs tradicionais exigem implementação manual ou bibliotecas externas (como Lombok) para gerar código repetitivo. Embora Lombok reduza a codificação manual, ele opera através do processamento de anotações e manipulação de bytecode, o que pode não permitir o mesmo nível de otimização profunda da JVM que as funcionalidades de linguagem nativas como os Records.10

### **Impacto das Otimizações da JVM (HotSpot, Biased Locking)**

O desempenho de hashCode() pode ser influenciado pela forma como a JVM lida com a identidade e o bloqueio de objetos. Por exemplo, o *código hash de identidade* (de Object.hashCode()) é gerado e armazenado em cache no cabeçalho do objeto na sua primeira chamada, o que pode ser uma operação relativamente lenta. As chamadas subsequentes são rápidas.17 No entanto, o cálculo de um  
hashCode() *baseado em valor* (como o de um Record) para um objeto *existente* pode ser mais rápido do que gerar um novo código hash de identidade.17  
O uso de invokedynamic para métodos de Record é uma otimização fundamental. Permite que a JVM ligue e otimize dinamicamente as chamadas de método, resultando em menos bytecode e potencialmente uma execução mais rápida, especialmente em caminhos de código frequentemente executados.23 O mecanismo  
invokedynamic permite a compatibilidade binária futura, o que significa que se uma nova e mais eficiente implementação de método bootstrap for introduzida numa futura versão do Java, as aplicações que utilizam Records podem beneficiar sem recompilação.23  
Uma consideração crítica de desempenho é que a chamada de Object.hashCode() (o código hash de identidade) num objeto o torna inelegível para *biased locking* no HotSpot. Se uma aplicação depende do *biased locking* para desempenho em sincronização de baixa contenção, a chamada de hashCode() nesses objetos pode introduzir sobrecarga. Os Records, ao fornecerem um hashCode() baseado em valor, evitam esta armadilha específica se o seu hashCode() for usado em vez do de identidade.15  
A afirmação de que "Java Records são 'Confiáveis' e Consequentemente Mais Rápidos" 21 indica que os Records não são meramente açúcar sintático, mas possuem um status privilegiado dentro da HotSpot JVM. Esta "confiança" provavelmente se traduz em otimizações diretas do compilador e do tempo de execução que não são concedidas a classes regulares ou mesmo àquelas aprimoradas por bibliotecas de manipulação de bytecode. O mecanismo  
invokedynamic 23 é um exemplo primordial de como essa confiança é aproveitada para o desempenho. Isso sugere que, para cenários onde os Records são adequados (portadores de dados imutáveis), eles não são apenas convenientes, mas também potencialmente a opção mais performática devido à sua profunda integração com as estratégias de otimização internas da JVM. Isso reforça a ideia de que o uso de recursos de linguagem nativos pode desbloquear benefícios de desempenho que são difíceis de obter de outra forma.  
A discussão sobre desempenho também destaca que "mais rápido" depende do contexto. Embora o hashCode baseado em valor para objetos *existentes* possa ser mais rápido do que gerar um *novo* código hash de identidade 17, a geração inicial de um código hash de identidade é lenta. Além disso, o impacto no  
*biased locking* 15 mostra que uma chamada aparentemente inócua de  
hashCode pode ter implicações de desempenho mais amplas e em nível de sistema relacionadas à concorrência. Isso enfatiza que a otimização de desempenho em Java é complexa e exige uma compreensão holística do funcionamento interno da JVM. Os desenvolvedores devem perfilar suas aplicações para identificar gargalos, em vez de confiar em afirmações generalizadas de "mais rápido". A escolha entre Records e classes tradicionais deve considerar não apenas a concisão do código e a imutabilidade, mas também as características de desempenho específicas de seus padrões de uso de hashCode e equals dentro do modelo de concorrência da aplicação.

**Tabela 2: Desempenho do hashCode() (Records vs. Outros)**

| Cenário / Tipo de Classe | Operação hashCode() | Desempenho (Qualitativo) | Fator Chave / Otimização | Notas |
| :---- | :---- | :---- | :---- | :---- |
| **Java Records** | Invocação | Mais rápido que POJOs/Lombok | invokedynamic, confiança da JVM | Otimização em tempo de execução |

## **5\. Personalizando o hashCode() em Java Records**

### **Quando e Como Sobrescrever a Implementação Padrão**

Embora os Records forneçam implementações padrão sensatas para equals() e hashCode(), o Java permite que os desenvolvedores as sobrescrevam.8 A razão principal para sobrescrever é quando a igualdade padrão baseada em valor (que considera todos os componentes) não corresponde à igualdade semântica desejada para um domínio específico. Por exemplo, se apenas um subconjunto de componentes deve determinar a igualdade.12  
Ao sobrescrever equals(), é crucial também sobrescrever hashCode() para manter o contrato de Object.hashCode(): objetos iguais devem ter códigos hash iguais. A falha em fazer isso levará a um comportamento incorreto em coleções baseadas em hash.12 O método utilitário  
java.util.Objects.hash(Object...) é recomendado para construir códigos hash personalizados, pois lida corretamente com nulos e tipos primitivos.12

### **Considerações para Componentes Mutáveis**

Records são "imutáveis superficialmente" (*shallowly immutable*). Isso significa que, embora seus componentes sejam referências final, se um componente em si for um objeto mutável (por exemplo, uma List ou um array), o estado desse componente mutável ainda pode ser alterado após a construção do Record.4  
Se um Record contiver componentes mutáveis e seus métodos equals() e hashCode() dependerem do estado desses componentes mutáveis, então a alteração do componente mutável *após* o Record ter sido colocado em uma coleção baseada em hash (como uma chave HashMap ou um elemento HashSet) pode quebrar a integridade da coleção. O código hash do objeto mudaria, mas sua posição na tabela hash não, tornando-o irrecuperável ou levando a um comportamento incorreto.12 Nesses casos, os desenvolvedores devem garantir que os componentes mutáveis nunca sejam modificados após a criação do Record (tratando-os efetivamente como imutáveis, por exemplo, fazendo cópias defensivas no construtor) ou sobrescrever explicitamente  
equals() e hashCode() para lidar com os componentes mutáveis de uma forma que preserve o contrato, o que muitas vezes significa *não* incluí-los no cálculo do código hash se sua mutabilidade for intencional.12  
A armadilha da "imutabilidade rasa" é um detalhe de design crítico. Embora os Records sejam promovidos como "portadores de dados imutáveis" 1, a possibilidade de ter componentes mutáveis 4 revela que, embora a  
*referência* a um componente seja final, o *objeto* para o qual ela aponta pode não ser imutável. Isso pode violar silenciosamente o contrato hashCode/equals se os componentes mutáveis não forem tratados com cuidado, especialmente quando os Records são usados como chaves em coleções de hash. Isso exige que os desenvolvedores permaneçam vigilantes quanto à imutabilidade de *todos* os componentes ao projetar Records. A conveniência dos Records não isenta o desenvolvedor de entender as implicações de imutabilidade de grafos de objetos complexos. Isso destaca um potencial "tiro no pé" se a distinção entre imutabilidade rasa e profunda não for compreendida.  
A capacidade de sobrescrever equals() e hashCode() 12 indica que a igualdade gerada automaticamente, baseada em componentes, pode nem sempre se alinhar com a "igualdade semântica" do domínio. Por exemplo, dois Records  
Movie podem ser considerados iguais se seus name e yearOfRelease corresponderem, independentemente do distributor.12 Isso reforça que os Records, embora opinativos, ainda são flexíveis o suficiente para se adaptar a requisitos de domínio específicos. No entanto, essa flexibilidade vem com a responsabilidade de implementar corretamente o contrato  
equals/hashCode, especialmente a regra de consistência para coleções baseadas em hash, que é fundamental para a correção e o desempenho.

## **6\. Conclusão e Principais Aprendizados**

Os Java Records representam uma evolução significativa na modelagem de dados, oferecendo uma abordagem concisa e eficiente para a criação de portadores de dados imutáveis. Ao automatizar a geração de métodos essenciais como equals(), hashCode() e toString(), eles reduzem drasticamente o código repetitivo, permitindo que os desenvolvedores se concentrem na lógica de negócios central.  
Um ponto crucial a ser compreendido é que o hashCode() de um Record é *computado* a partir de seus componentes e *não* é explicitamente armazenado em cache em um campo interno por padrão, o que o diferencia da implementação de java.lang.String. No entanto, a Java Virtual Machine (JVM), especialmente o HotSpot, aplica otimizações sofisticadas em tempo de execução, incluindo o uso de invokedynamic, para tornar o cálculo dos métodos de Record, incluindo hashCode(), altamente eficiente. Esse status de "confiança" concedido aos Records pela JVM pode resultar em um desempenho superior em comparação com POJOs tradicionais ou classes geradas por Lombok.  
É fundamental distinguir entre o hashCode() baseado em valor dos Records e o Object.identityHashCode(). Este último *é* armazenado em cache pela JVM no cabeçalho do objeto, mas sua invocação pode ter implicações para o *biased locking*, uma otimização de concorrência da JVM.  
Embora os Records sejam projetados para serem imutáveis, eles são "imutáveis superficialmente". Isso exige cautela por parte dos desenvolvedores se os Records contiverem componentes mutáveis. A modificação de tais componentes após a criação do Record pode comprometer o contrato equals/hashCode e levar a um comportamento incorreto em coleções baseadas em hash. Nesses casos, a sobrescrita dos métodos equals() e hashCode() padrão é possível e necessária para alinhar a igualdade semântica com a igualdade baseada em componentes, mas exige uma adesão cuidadosa ao contrato de Object.  
A integração de invokedynamic e o status de "confiança" dos Records sugerem que eles não são apenas um recurso isolado, mas um elemento fundamental para futuras melhorias da JVM e da linguagem. Sua natureza bem definida e imutável os torna candidatos ideais para otimizações adicionais. A adoção de Records alinha um código com a direção do Java moderno, potencialmente gerando benefícios de futuros avanços da JVM sem alterações no código. Isso posiciona os Records como uma escolha estratégica para novos desenvolvimentos em Java 16 e versões posteriores.  
Por fim, embora os Records ofereçam imensa conveniência ao abstrair o código repetitivo, a discussão sobre a imutabilidade rasa, as implementações não normativas de hashCode e as interações com os internos da JVM (como o *biased locking*) demonstra que uma compreensão profunda desses mecanismos subjacentes ainda é crucial para aplicações robustas e performáticas. Embora os Records simplifiquem casos de uso comuns, eles não eliminam a necessidade de conhecimento especializado em cenários complexos. O uso eficaz dos Records requer a compreensão de *quando* seus comportamentos padrão são suficientes e *quando* uma personalização mais profunda ou a consciência das interações da JVM são necessárias.
